# Remote Desktop (for developers)

Developers log in to the server's Windows desktop with **Remote Desktop**,
the same way you would sit in front of it. Two things must be true first:

1. Their **internet address is on the server's guest list** (the
   firewall). Everyone else on the internet is turned away.
2. They can see the **login** in 1Password (vault `azure-infra-logins`).

The person who looks after the project (the operator, with Claude's help)
does the first part, and shares the vault for the second.

## Give a developer access (operator, about 10 minutes)

Ask Claude: *"Give <name> Remote Desktop access."* It walks you through
this:

1. **Ask the developer for their internet address.** They open
   <https://ifconfig.me> on the network they work from and send you the
   number, for example `203.0.113.7`. (It is not a secret, but it is
   private: it stays in 1Password, never in GitHub.)
2. **Add it to the guest list.** In 1Password, vault `azure-infra`, item
   `sql-server-settings`, edit `rdp_source_cidrs`. Add the address with
   `/32` at the end, separated from the others by a comma:
   `198.51.100.7/32, 203.0.113.7/32`. Save.
3. **Tell the robot.** On GitHub: **Actions** > **Infrastructure** > **Run
   workflow** (branch `main`) > **Run workflow**. When `plan` is green, it
   should only change `allow_rdp` (Claude can read it for you). Click
   **Review deployments** > **Approve and deploy**. Takes a minute.
4. **Share the logins vault.** In 1Password, open vault
   `azure-infra-logins` > **People** (or **Manage access**) > add the
   developer. **Never** share the `azure-infra` vault with developers: it
   holds the keys to Azure itself.

!!! info "Behind the scenes"
    The firewall (an Azure "network security group") has a rule that opens
    port 3389 (Remote Desktop) only to the addresses in
    `rdp_source_cidrs`. The robot reads that list from 1Password on every
    run and updates the rule. The list never appears in the public
    project; plan output shows it as `(sensitive value)`.

## Connect (developer)

1. In 1Password open **`sql-web-01 Windows admin`** (vault
   `azure-infra-logins`). It has:
    - **username**: `azureadmin`
    - **password**: long and random (generated by 1Password when the
      server was built)
    - **website**: `rdp://<server address>`
2. Open Remote Desktop:
    - **Windows**: Start menu > type **Remote Desktop Connection**. Computer:
      the server address (the part after `rdp://`). **Show Options** > User
      name: `azureadmin`. **Connect**, then paste the password.
    - **Mac**: install **Windows App** from the App Store. **+** > **Add
      PC**, PC name: the server address, user account: `azureadmin` and
      the password. Double-click the PC.
3. The first time, a warning says the server's identity cannot be
   verified (its certificate is self-made). Tick "Don't ask me again" and
   click **Yes** / **Continue**.

SQL Server Management Studio, if needed, runs on the server itself: log in
to Windows, start SSMS, server `localhost`, Windows Authentication; or SQL
login `sqladmin` from `sql-web-01 SQL login` (same vault).

## It stopped working

| Symptom | Usual cause | Fix |
|---|---|---|
| Connection times out | Their internet address changed (home connections change now and then), or they are on a different network | Check <https://ifconfig.me> again; the operator updates the list and runs the workflow |
| "Password incorrect" | Copied with a space, or the password was changed | Copy again from 1Password |
| Worked for others, not for one person | Their address is missing or mistyped in the list | Check the list in `sql-server-settings` |
| Nobody can connect | Server stopped, or the list was emptied | Azure portal > the VM: is it **Running**? Ask Claude to check the last run |

## Remove access (someone leaves)

1. Remove their address from `rdp_source_cidrs`, run the workflow,
   approve.
2. Remove them from the `azure-infra-logins` vault.
3. Change the shared passwords they knew: ask Claude or Andrew (see
   [Operations: passwords](operations.md#passwords)).

Everyone shares the one `azureadmin` login today. For a larger team,
Andrew can create a personal Windows account for each developer on the
server, so access can be removed per person.
